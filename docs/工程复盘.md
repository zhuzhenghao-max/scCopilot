## 一、项目背景与目标

### 1.1 问题定义

单细胞 RNA 测序（scRNA-seq）是生物医学研究的核心技术，但分析流程存在两个痛点：

1. **技术门槛高**：学生物的人不会写代码，会写代码的人不懂生物
2. **结果不可追溯**：AI 给出的细胞类型预测缺乏证据支撑，容易"幻觉"

### 1.2 产品目标

构建一个**零门槛、可追溯、防幻觉**的单细胞分析工作台：

- 学生上传 .h5ad 文件，点击 UMAP 上的细胞，3 秒内看到 AI 解读
- 每个解读结论都能追溯到具体的 marker 基因证据
- 证据不足时 AI 主动拒绝回答，而不是编一个名字

### 1.3 技术目标

| 目标 | 量化指标 |
|------|----------|
| 可复现 | 同一份数据 + 同一组参数 = 完全相同的结果 |
| 可追溯 | 每个 AI 结论都能回溯到 marker 证据表 |
| 防幻觉 | Critic Agent 审查不一致时返回 escalate |
| 高性能 | 调参秒级响应（recluster 快路径） |
| 可测试 | 73 个单元测试，全部通过 |

## 二、架构设计

### 2.1 分层架构

```
┌─────────────────────────────────────────┐
│           前端层 (app/main.py)          │  Streamlit + st.fragment
├─────────────────────────────────────────┤
│         AI 解读层 (ai/explainer.py)     │  LLM 调用 + 本地规则
├─────────────────────────────────────────┤
│      多智能体编排层 (agents/)           │  Planner/Annotator/Critic
├─────────────────────────────────────────┤
│         核心层 (core/)                  │  Pipeline + KG + Provenance
├─────────────────────────────────────────┤
│         数据层 (data/)                  │  .h5ad + CSV + JSON
└─────────────────────────────────────────┘
```

**设计原则**：
- 上层只调用下层，不反向依赖
- 每层职责单一，可独立测试
- 数据流单向，易于调试

### 2.2 核心模块

#### 2.2.1 状态机引擎 (core/pipeline.StateAwarePipeline)

**问题**：原有 `run_pipeline()` 是一个大函数，无法中途暂停或回退。

**方案**：引入状态机模式，将流水线拆分为 4 个状态：

```
raw → qc_passed → embedded → clustered
```

**实现**：
```python
class StateAwarePipeline:
    def __init__(self, adata, config=None):
        self.state = "raw"
        self.provenance = ProvenanceTracker()
    
    def run_qc(self):
        if self.state != "raw":
            raise StateError(f"当前状态为 {self.state}，无法执行 QC")
        # ... 执行 QC
        self.provenance.log_step("apply_qc", ...)
        self.state = "qc_passed"
    
    def run_embedding(self):
        if self.state != "qc_passed":
            raise StateError(...)
        # ...
        self.state = "embedded"
    
    def run_clustering(self):
        if self.state != "embedded":
            raise StateError(...)
        # ...
        self.state = "clustered"
        return PipelineResult(...)
```

**收益**：
- 非法转换立即报错（如跳过 QC 直接 embedding）
- 每步操作自动记录审计信息
- 支持 `run_full()` 一键跑完全流程

#### 2.2.2 知识图谱检索 (core/kg_retriever.py)

**问题**：AI 预测细胞类型时缺乏生物学先验知识。

**方案**：内置 Cell Ontology 知识图谱（20 种免疫细胞），用 Jaccard 相似度匹配 marker 基因。

**实现**：
```python
CELL_ONTOLOGY = {
    "CL:0000624": {
        "name": "CD4+ T cell",
        "parent": "CL:0000084",  # T cell
        "markers": ["CD3D", "CD3E", "CD4", "IL7R"]
    },
    # ... 共 20 种
}

def retrieve(marker_genes, top_k=5):
    candidates = []
    for cl_id, info in CELL_ONTOLOGY.items():
        matched = set(marker_genes) & set(info["markers"])
        score = len(matched) / len(set(marker_genes) | set(info["markers"]))
        # 父类加分
        if info["parent"] in [c["cl_id"] for c in candidates]:
            score += 0.1
        candidates.append({
            "cl_id": cl_id,
            "name": info["name"],
            "score": score,
            "matched_markers": list(matched)
        })
    return sorted(candidates, key=lambda x: -x["score"])[:top_k]
```

**收益**：
- AI 预测有生物学先验支撑
- 父类层级一致性检查（如 CD4+ T cell 的父类是 T cell）
- 可解释性强（matched_markers 明确展示匹配了哪些基因）

#### 2.2.3 多智能体编排 (agents/orchestrator.py)

**问题**：单次 LLM 调用容易"幻觉"，缺乏审查机制。

**方案**：引入 Planner → Annotator → Critic 三阶段工作流。

**实现**：
```python
def run_annotation_workflow(cluster_id, marker_genes, ...):
    # 1. Planner：评估证据，决定是否调用 LLM
    evidence = assess_evidence(marker_genes, ...)
    planner = PlannerAgent()
    plan = planner.plan(cluster_id, marker_genes, evidence)
    
    # 2. Annotator：KG 检索 + LLM 调用
    annotator = AnnotatorAgent()
    itp, kg_candidates = annotator.annotate(cluster_id, marker_genes, evidence, plan, ...)
    
    # 3. Critic：审查结果，检查一致性
    critic = CriticAgent()
    critique = critic.critique(itp, kg_candidates, evidence)
    
    return {
        "interpretation": itp,
        "kg_candidates": kg_candidates,
        "critique": critique,  # {"status": "approve" | "escalate", "reason": ...}
        "trace": [...]  # Agent 执行轨迹
    }
```

**Critic 审查逻辑**：
1. 如果 Annotator 已拒绝 → 直接透传 escalate
2. 检查预测类型是否在 KG 候选里（或为子类/父类）
3. 检查证据是否充足（n_usable >= 3）
4. 如果冲突或薄弱 → escalate
5. 否则 → approve

**收益**：
- 防幻觉：Critic 审查不一致时返回 escalate
- 可追溯：trace 记录每个 Agent 的执行轨迹
- 职责单一：每个 Agent 可独立测试与替换

#### 2.2.4 审计追踪 (core/provenance.py)

**问题**：分析流程缺乏审计信息，无法复现。

**方案**：ProvenanceTracker 记录每步操作的工具名、参数、结果摘要、耗时。

**实现**：
```python
@dataclass
class StepRecord:
    tool_name: str
    params: dict[str, Any]
    result_summary: dict[str, Any]
    timestamp: float
    duration_s: float

class ProvenanceTracker:
    def log_step(self, tool_name, params, result_summary, *, duration_s=0.0):
        record = StepRecord(tool_name, params, result_summary, duration_s=duration_s)
        self._steps.append(record)
    
    def export_json(self):
        return {
            "session_start": self._start_time,
            "total_steps": len(self._steps),
            "steps": [s.to_dict() for s in self._steps]
        }
```

**收益**：
- 完整审计：每步操作都有记录
- 可复现：export_json() 导出完整报告
- 前端展示：在「QC 漏斗 / 耗时 / 导出」区域展示溯源信息

#### 2.3.2 Agent 思考过程可视化

**问题**：AI 卡片只展示结论，用户不知道 AI 是怎么想的。

**方案**：用 st.status + 自定义时间线 HTML 展示 Agent 执行轨迹。

**实现**：
```python
with st.status("多智能体工作流启动...", expanded=True) as status:

# 时间线展示
if trace:

        <div class="sc-timeline-step">
            <div class="sc-timeline-dot">🧠</div>

```

**收益**：
- 用户能看到 AI 的思考过程
- 增强可信度和可解释性

**收益**：
- 防幻觉机制可视化
- 用户理解 AI 的局限性

## 三、关键技术决策

### 3.1 为什么用状态机而不是函数链？

**备选方案**：
```python
def run_pipeline(adata, config):
    adata = apply_qc(adata, config)
    adata = normalize(adata, config)
    adata = find_hvg(adata, config)
    # ...
    return PipelineResult(adata)
```

**问题**：
- 无法中途暂停（如只想跑 QC 不跑聚类）
- 无法回退（如 QC 参数调错了要重跑全流程）
- 缺乏审计信息（不知道每步耗时多少）

**状态机方案**：
- 每步操作都是显式状态转换
- 非法转换立即报错
- 自动记录审计信息

### 3.2 为什么用多智能体而不是单次 LLM 调用？

**备选方案**：
```python
def interpret_cluster(marker_genes, ...):
    prompt = build_prompt(marker_genes, ...)
    reply = call_llm(prompt)
    return parse_reply(reply)
```

**问题**：
- LLM 可能"幻觉"（预测一个不存在的细胞类型）
- 缺乏审查机制（不知道预测是否合理）
- 不可追溯（不知道 LLM 是怎么想的）

**多智能体方案**：
- Planner 评估证据，决定是否调用 LLM
- Annotator 调用 KG 检索 + LLM
- Critic 审查结果，检查一致性
- trace 记录每个 Agent 的执行轨迹

### 3.3 为什么用 Jaccard 相似度而不是余弦相似度？

**备选方案**：
```python
from sklearn.metrics.pairwise import cosine_similarity

def retrieve(marker_genes, top_k=5):
    vec = encode_genes(marker_genes)  # one-hot encoding
    scores = cosine_similarity(vec, kg_vectors)
    return top_k(scores)
```

**问题**：
- 余弦相似度考虑了基因表达量，但 KG 里只有 marker 列表，没有表达量
- 计算复杂度高（需要矩阵运算）

**Jaccard 方案**：
- 只考虑基因是否匹配，不考虑表达量
- 计算简单（集合交集 / 集合并集）
- 可解释性强（matched_markers 明确展示匹配了哪些基因）

### 3.4 为什么用 st.fragment 而不是 st.cache_data？

**备选方案**：
```python
@st.cache_data
def run_ai(cluster_id, result, params):
    return interpret_cluster(...)
```

**问题**：
- st.cache_data 缓存的是函数返回值，不是 UI 组件
- 点击 UMAP 还是会重跑整个页面

**st.fragment 方案**：
- 隔离 UI 组件，只刷新局部
- 响应速度从 3-5s 降到 <1s

### 3.5 为什么逐细胞判型不用 `sc.tl.score_genes`？

**最初的写法**（第一版异质性判定）：
```python
sc.tl.score_genes(adata, gene_list=panel, score_name="s")   # 对照组 = 传进去那些列的分箱抽样
label = argmax over types(s)   # 领先第二名 margin=0.5 才算数
```

**两个致命问题（都是实测出来的，不是理论担心）**：

1. **分数量纲随切片变化，甚至直接打不出分**。`score_genes` 的对照组是从"你传给它的那些列"里
   分箱抽的：演示数据 5 个簇用"面板 ∪ 2000 HVG"时 gap 中位是 0.133~0.144（低质量簇 0.222），
   改用"全基因 2452 列"则变成 0.147~0.166（低质量簇 0.246）；而只喂面板基因时对照组一个都
   取不出来，直接抛 `RuntimeError: No control genes found in any cut`（复跑
   `_research/diag_scoring_space.py`、`_research/diag_het_scale.py`）。
   于是**绝对阈值 margin=0.5 没有意义**：5 个簇的主标签全被判成 Unassigned，连 marker 检出率
   98–100% 的干净 T/B/单核/NK 簇也只有 assigned 3%–5%（低质量簇 19%），Critic 见簇就拦。
   一个把正确答案全拦下的闸门，比没有闸门更糟。
2. **argmax 在共享 marker 之间是掷硬币**。NK 簇里 CD8+ T 面板一个判别基因都没有
   （CD8A/CD8B 不在这份矩阵里），却靠共享的 GNLY/NKG7/PRF1 赢下 49% 的细胞。

**改成的口径**：`z(c,t) = (本细胞判别基因平均表达 − 参照细胞同统计量均值) / 参照细胞标准差`，
参照细胞是**本簇之外**的细胞（多于 4000 个时等距抽样，不用 RNG）。

- 参照是数据本身，不是抽出来的对照组 → 切片方式不影响量纲；
- 判别基因（别的候选类型面板里没有的基因）→ 共享 marker 不参与掷硬币；
- 参照细胞不足 50 个 → `not_assessed` 并说明"这一簇几乎就是整份数据，没有参照系可言"，
  而不是硬造一个相对结论；
- 每个数字都能在 X 矩阵上逐细胞复算，`z_median`、`n_reference_cells` 原样进前端。

**中途否决的两个方案（记下来免得再走一遍）**：
- 簇内列内 z 标准化：判型被打散成 8–16% 的均匀噪声，等于没有判型；
- "检出即阳性"的绝对口径：这份数据每个细胞几乎所有基因都非零，NK/B/单核阳性率 88–100%，
  类型之间分不开（`_research/diag_positive_rate.py`）。

**教训**：阈值必须跟着一个**量纲稳定**的统计量走。自称"每个数字都能复现"的实现里，
先问"这个数的单位是什么、换一种切片方式它还一样吗"，再谈阈值取多少。

### 3.6 为什么不接预训练细胞类型模型（CellTypist 实测否决）

有人会问：能不能像 AlphaFold 那样，接一个预训练模型当"第三票"？我们实测了最轻量的一条
路线——CellTypist（Sanger 官方 LogisticRegression 模型，Immune_All_High.pkl，32 类 /
6639 训练基因，sha256 `a715fec3…448`，复跑 `python -u -X utf8 _research/spike_celltypist.py`）：

| 簇 | 真值 | CellTypist 逐细胞最常见标签 | 我们的判定 |
|----|------|------------------------------|------------|
| 0 | T | Double-positive thymocytes 86% | CD4+ T 细胞 100% |
| 1 | B | B cells 89% | 初始 B 细胞 (naive B) 100% |
| 2 | Mono | Double-positive thymocytes 94% | 经典单核细胞 (CD14+) 100% |
| 3 | NK | ILC 85% | NK 细胞 98% |
| 4 | 低质量 | **B cells 54%（高置信度错标）** | ambiguous → 主动拒答 |

- 判对 1/5，簇平均概率最高只有 0.04——模型是在 50 个残存特征上对噪声做 argmax。
- 最致命的是簇 4：对线粒体 13%、只有 7% 判读得出的低质量簇，它给了 54% 的"B cells"。
  预训练模型拿不出"这一票依据哪个数字"，这种幻觉置信度正是 Critic 闸门要拦的东西。
- 根因不是模型差（它是在真实 PBMC 上发表验证过的），而是演示矩阵只有 2452 个基因、
  真实免疫基因约 30 个 → 6639 个训练特征只对上 50 个（0.75%）。换成真实全转录组数据
  结论可能反转，但那不是我们的演示口径。
- **结论：否决"接预训练模型"，维持 KG 名字重合 + 表达层核实 + 异质性判定三闸门。**

顺带记录 celltypist 1.7.1 的两个坑（复跑必踩）：

- `Model.load` 用 `'/' not in model` 判断传的是名字还是路径——Windows 反斜杠路径会被当成
  模型名，触发"本地无模型 → 全量下载 61 个"的副作用（实测卡 25 分钟就是它）；路径必须写成正斜杠。
- `celltypist.annotate` 没有 `prob_matrix` 形参，概率矩阵从返回值的 `probability_matrix` 拿。

| 18 | 同一份数据稠密/稀疏矩阵的 z 分末位不同，被近零参照标准差放大成 0.06 的可见差 | `_stat` 两条路径统一转 float64 后求行均值，保证逐位复现 |
| 19 | 亚簇拆分只认 `highly_variable`，类型信号不在 HVG 注释里时真亚群被假报成"零散噪声" | 拆分空间取"判别基因 ∪ 全数据集 HVG"（只改副本，不写回共享 adata） |
| 20 | 小鼠写法（Cd3d）与知识库大写（CD3D）对不上时整批类型打不出分，判定假报"读不出" | `_var_map` 用大写键索引、按矩阵实际写法取列 |
| 21 | 静态站页脚写"同一命令可逐字节复现"，实测连跑两次导出并不成立（每步耗时与 Agent 时间戳必然变化） | 改成准确表述：分析结果逐字节一致，耗时/时间戳只是审计信息；导出脚本 [4/4] 校验顺带断言每簇都有异质性判定，漏传 `adata` 会直接失败 |

### 5.2 测试设计原则

1. **独立性**：每个测试用例独立运行，不依赖其他用例
2. **可重复**：使用固定 seed（如 `build(seed=42)`）确保结果一致
3. **快速反馈**：分离测试文件，独立运行（避免 numba JIT 编译等待）
4. **边界测试**：测试非法输入（如空 marker 列表、非法状态转换）
5. **断言"复现"本身**：异质性判定用 `test_numbers_reproduce_exactly`（同数据重跑逐字相同）
   和 `test_dense_and_sparse_agree`（换矩阵存储格式也相同）把口号钉成用例——后者真的抓到了
   float32 稀疏行均值与稠密行均值末位不同、被近零标准差放大的 bug。
6. **夹具要有被测口径要求的前提**：判型分数是"相对簇外参照细胞"的，单簇夹具在新口径下
   只会得到 `not_assessed`。上一版全绿不代表口径对，只是前提没被检验——夹具补参照簇之后
   才发现期望值要整批重设。
7. **断言要打在真正承载信息的通道上**：`st.caption` 在 AppTest 里不属于 `at.markdown`，
   得用 `at.get("caption")`。写错时测试会红，但红的是测试，不是应用。

### 5.3 关键测试用例

#### 测试状态机正常转换
```python
def test_state_machine_transitions():
    adata = build(seed=42)
    cfg = PipelineConfig(n_markers=5, resolution=0.8)
    sp = StateAwarePipeline(adata, config=cfg)
    assert sp.state == "raw"
    
    sp.run_qc()
    assert sp.state == "qc_passed"
    
    sp.run_embedding()
    assert sp.state == "embedded"
    
    result = sp.run_clustering()
    assert sp.state == "clustered"
```

#### 测试 Critic 防幻觉机制
```python
def test_critic_escalates_on_mismatch():

    evidence = assess_evidence(["CD3D", "CD3E"], cluster_stats={"n_cells": 50})
    
    itp = Interpretation(
        cluster="0",
        predicted_type="B cell",  # 与 KG 候选不一致
        ...
    )

    critique = critic.critique(itp, kg_candidates, evidence)
```
